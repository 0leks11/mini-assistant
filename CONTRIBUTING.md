# Разработка mini-assistant

Эти правила применяются и к человеку, и к агенту. Начинай с [AGENTS.md](AGENTS.md).
Общие решения и исследования рабочего каталога доступны через [корневой README](../README.md),
если репозиторий расположен внутри `gpt-mini`.

## Цикл изменения

1. **Понять задачу.** Прочитай затронутый код, `git status --short` и существующие
   тесты. Определи вход, ожидаемый результат, ошибки и ограничения Mini.
2. **Спланировать.** Для небольшого исправления достаточно короткого плана.
   Для нового протокола, аудиоконвейера или миграции запиши контракт, альтернативы,
   границы, проверки и откат до реализации; общий шаблон находится в
   [../docs/templates/PLAN.md](../docs/templates/PLAN.md).
3. **Реализовать.** Один diff решает одну задачу. Изменения зависимостей сопровождай
   обоснованием размера, лицензии и доступности ARM32/native-библиотек.
4. **Проверить.** Используй матрицу ниже. Укажи реальные команды, результаты,
   ограничения окружения и пропущенные проверки. Не называй сборку тестом голоса.
5. **Отревьюить.** Сначала ищи ошибки поведения и регрессии, затем упрощай код.
   Проверь тайм-ауты, очереди, переподключение, освобождение ALSA, утечки секретов
   и поведение при отказе облака/HA. Для сложного изменения полезно независимое ревью.
6. **Зафиксировать.** Проверь staged diff; используй коммит `type(scope): описание`
   (`feat`, `fix`, `test`, `docs`, `refactor`, `chore`). Чужие изменения не добавляй.

## Проверки

| Изменение | Минимальная проверка | Что она не подтверждает |
|---|---|---|
| Только Markdown | Ссылки, примеры команд, согласованность инструкций, `git diff --check` | Сборку или работу устройства |
| Rust-код/зависимости | `./scripts/check.sh` и тесты затронутого поведения | ARM32 ABI и реальный звук |
| Аудиовыход через `aplay` | Mock-тесты запуска/завершения процесса; перед deployment — ARM-сборка и проверка `aplay` на Mini | Работу DSP и физического выхода без стендового теста |
| Cross/native/build | ARM-сборка и инспекция ELF/зависимостей | Готовность полного голосового цикла |
| Deployment/аудио | Синтаксические проверки; ограниченный стендовый тест с откатом | Остальные сценарии без проверки |
| HA/облако | Тесты протокола с mock-сервером, ошибок, тайм-аутов и разрешённых действий | Успех настоящего аккаунта/устройства |

Локальная команда запускается из любого каталога:

```bash
/path/to/mini-assistant/scripts/check.sh
```

Она выполняет:

```bash
cargo fmt --all -- --check
cargo clippy --locked --all-targets -- -D warnings
cargo test --locked --all-targets
```

Нужен Rust toolchain с `rustfmt` и `clippy`. Текущий Rust-код не зависит от
`alsa`/`alsa-sys`: воспроизведение передаётся отдельному процессу `aplay`.
Поэтому `libasound2-dev` и `pkg-config` сейчас не являются требованиями этих
host-проверок. Cargo может скачать зависимости при первом запуске.
Команда не запускает основной бинарь, не загружает `.env`, не обращается к
облачным/HA API и не выполняет deployment. Новые тесты также должны использовать
изолированные фикстуры/mocks, а не реальные секреты или физические устройства.
Успешный `cargo test` с **0 тестов** подтверждает только сборку test harness;
это не покрытие поведения.

CI [checks.yml](.github/workflows/checks.yml) запускает те же host-проверки на
Linux и macOS после push/PR в GitHub. Без публикации репозитория CI здесь не
выполняется. CI не устанавливает `aplay` и не запускает основной бинарь;
Linux runner также не подтверждает работоспособность аудиовыхода.
CI не является ARM-сборкой и не проверяет Mini.

Перед аппаратным тестом отдельно проверь доступность исполняемого `aplay`
на Mini, его ABI и native-зависимости, поддерживаемый ALSA device и точные
параметры PCM. Затем выполни ограниченный тест с фактическим подтверждением
звука. Статический Rust-бинарь не устраняет зависимость runtime от `aplay`,
его библиотек, драйверов и настройки аудиотракта.

Для подготовки артефакта, когда настроены `cross`, Docker и native-зависимости:

```bash
./scripts/build.sh
file target/armv7-unknown-linux-musleabihf/release/mini-assistant
# Используй доступный readelf/llvm-readelf из toolchain:
readelf -h -l -d target/armv7-unknown-linux-musleabihf/release/mini-assistant
```

Проверь ARM/ELF32, hard-float ABI, interpreter и записи `NEEDED`; для динамических
библиотек нужен совместимый набор на Mini. Не запускай `ldd` на неизвестном
бинарнике и не обещай полную статическую линковку только по имени target.

## Готовность изменения

- Описано фактическое изменение поведения и проверены существенные ошибки.
- Релевантные проверки прошли либо явно указана существующая ошибка/блокер.
  Не скрывай baseline failure и не ослабляй проверки ради зелёного статуса.
- В diff нет настоящих credentials, сырого голоса, личных диалогов и чужих правок.
- Документы различают «предложено», «реализовано», «проверено локально»,
  «подтверждено на Mini». Новые API/провайдеры проверены по первичным источникам.
- Для аппаратного изменения записаны точная версия артефакта, условия,
  наблюдения и результат восстановления исходного состояния.
- Итог пользователю содержит результат, проверки и оставшиеся ограничения.

## Git и deployment

Перед staging используй явный список файлов и просмотри `git diff --cached`.
Не применяй `git add .`, когда рядом есть незавершённая работа. Не переписывай
историю, не публикуй и не разворачивай изменение без соответствующего запроса.
Проверки выполняй на текущем дереве; если в нём есть чужие изменения,
не приписывай результат одному своему коммиту.

`scripts/deploy.sh` — отдельная операция с реальным устройством, **не** проверка
кода. Перед использованием прочитай текущую реализацию, установи её side effects
и проверь план отката. Документационная правка не требует ни deployment,
ни запуска микрофона, ни отключения `maind`.

Источники настройки CI: [actions/checkout](https://github.com/actions/checkout),
[dtolnay/rust-toolchain](https://github.com/dtolnay/rust-toolchain).
