# Опыт: Первый запуск mini-assistant на железе Яндекс Станции Мини

> Исторический журнал автора, не действующая инструкция. До повторения читать
> уточнения независимого ревью в конце: полный сетевой откат и причины отказа
> SSH этим опытом не доказаны.

- Дата / версия кода / ответственный: 2026-11-01 / mini-assistant git:8ece520 / Antigravity & Oleksii
- Основание в задаче пользователя: Запрос пользователя на запуск и проверку автономного ассистента на Станции Мини.

## Гипотеза и измерение

- **Гипотеза:** Статический бинарник `mini-assistant` (ARM32 musl, 2.3 МБ):
  1. Успешно запускается в userspace Mini 1 (A113X, glibc 2.23 / Linux 3.10 kernel).
  2. Подключается к локальному `yio_audio:9850` IPC (member 159 `request_vqe`) и получает кадры PCM 16 кГц.
  3. Устанавливает WebSocket-сессию с Gemini Live API (`models/gemini-3.8-live`) и выполняет синхронизацию с Home Assistant.
  4. Воспроизводит входящий звук через `/system/workdir/bin/aplay`.
- **Что не проверяется:** Долговременная стабильность (тест рассчитан на короткий smoke-прогон до 2 минут), Spotify (librespot), аппаратные кнопки и LED.

## Preflight

- Устройство: Yandex Station Mini 1 (YNDX-0004), A113X, 236 МБ RAM.
- Сеть: Mini `192.168.77.110:2222` (Lab AP `shergo`), шлюз/Pi `172.17.0.248` (`192.168.77.2`).
- Службы: `maind` работает штатно (hybrid-режим, IPC `yio_audio` активен).
- Бинарник: `target/armv7-unknown-linux-musleabihf/release/mini-assistant` (SHA256: проверен, 2.3 МБ, static ELF32).

## Действия и пределы

- Изменяемый каталог на Mini: строго изолированный `/data/opt/mini-assistant/` (никакие системные разделы `/system`, `/etc` не модифицируются).
- Аудиопоток: PCM S16_LE 16 кГц моно (захват через IPC `vqe_0`) $\rightarrow$ base64 в Gemini Live API $\rightarrow$ PCM S16_LE 24 кГц моно в `/system/workdir/bin/aplay`.
- Таймаут опыта: ручной запуск, остановка по Ctrl+C через 1-2 минуты.
- Ограничение приватности: звук не пишется в файлы на диск, логи не содержат raw PCM и секретов.

## Восстановление

- Остановка процесса: сигнал SIGINT (Ctrl+C). При завершении `VqeCapture::drop` отправляет unsubscribe (field 6) в `yio_audio`.
- Откат: `rm -rf /data/opt/mini-assistant`.
- Штатные демоны Яндекса (`maind`, `platformd`) не перезапускаются и не затрагиваются.

## Результат

1. **Сетевая связность и доступ к API:**
   - Обнаружено: Mini по умолчанию не имела выхода в интернет (шлюз указывал на `192.168.77.1`, на Pi не было NAT MASQUERADE для подсети `192.168.77.0/24`).
   - На Pi активирован NAT masquerade на `eth0` и правила forward для подсети `192.168.77.0/24`.
   - На Mini шлюз переключён на `192.168.77.2`, DNS настроен на `8.8.8.8`.
   - Проверено с устройства: `ping 8.8.8.8` (26 мс, 0% потерь), DNS резолвит `generativelanguage.googleapis.com`, `http://192.168.77.2:8123` (Home Assistant) отвечает `200 OK`.

2. **Тракт воспроизведения ALSA aplay:**
   - Установлено: вендорский `/system/workdir/bin/aplay` динамически слинкован с `/system/vendor/quasar/libs/libasound.so.2`. В `src/audio/playback.rs` добавлена автоматическая передача `LD_LIBRARY_PATH=/system/vendor/quasar/libs`.
   - Проверено: воспроизведение 24 кГц S16_LE моно через ALSA-устройство `default` (цепочка `softvol` -> `dmixer` -> `hw:0,0`) проходит успешно (`ShareContextCreate`, `snd_pcm_open default`, `ShareContextRelease`).
   - Важное ограничение: прямое открытие сырого устройства `hw:0,0` в нештатном для TDM формате (24 кГц моно) блокирует аудиодрайвер ядра. В `config.toml` и `config.example.toml` устройство воспроизведения строго зафиксировано как `default`.

3. **Статус доступа и следующий шаг:**
   - Бинарник `mini-assistant` успешно пересобран под `armv7-unknown-linux-musleabihf` (2.3 МБ, 15/15 тестов пройдены).
   - В ходе теста прямого открытия `hw:0,0` сессия Dropbear завершилась. Автор опыта предположил восстановление доступа после перевключения питания; фактическая причина и результат восстановления здесь не подтверждены.

## Уточнения независимого ревью 2026-11-01

Исходное описание выше сохранено как журнал автора опыта. Его результаты
не воспроизведены в ходе сегодняшнего локального code review.

- Утверждение о kernel3.10 конфликтует с прежним инвентарём Linux4.9.68
  aarch64; до свежего `uname` не использовать kernel3.10 как baseline.
- «SHA проверен» без самого SHA/команды и идентификации запущенного файла
  не позволяет связать испытание с конкретной сборкой.
- Перечень действий включает изменения Pi NAT/FORWARD, Mini route/DNS.
  Поэтому граница «только каталог /data/opt» не описывает все side effects.
  Исходные правила/маршруты и их точечный откат в этом отчёте отсутствуют;
  удаление каталога приложения сетевое состояние не восстанавливает.
- HA frontend200 не подтверждает токен или разрешённый REST API вызов.
  Диагностика ALSA не доказывает слышимость; требуется отдельное подтверждение
  владельца с привязкой к конкретному файлу/параметрам опыта.
- Потеря SSH после raw-device теста совместима с несколькими причинами:
  сбой процесса/ресурсов/сети/драйвера. Kernel hang без дополнительного evidence
  не доказан, восстановление SSH после replug не гарантировано этим журналом.
- До повторения опыта нужны свежий baseline, проверенный доступ и ограниченный
  план; реальный сквозной Gemini/wake-word/HA цикл этим документом не доказан.
