# Правила агентов: mini-assistant

Общие правила рабочего каталога находятся в [../AGENTS.md](../AGENTS.md),
порядок разработки — в [CONTRIBUTING.md](CONTRIBUTING.md).
При отдельном клонировании этого репозитория родительский файл может отсутствовать;
действуют доступные инструкции и правила ниже.

## Цель и границы

- Цель — полная замена компонентов ПО Яндекса на оригинальной Mini 1. Наш
  прикладной стек — Rust, runtime/голос/музыка исполняются локально на Mini;
  Pi обслуживает только Home Assistant. Vendor frontend и Pi gateway —
  временные лабораторные зависимости, не конечная архитектура.
- Разделяй цель, реализацию в коде и подтверждённую работу на устройстве.
  Наличие модуля или успешная сборка не доказывают готовность голосового диалога.
- Исследуй существующий код до выбора архитектуры; не объявляй конкретный облачный
  провайдер, OAuth, wake-word или Spotify реализованными без подтверждения.
- Отвечай пользователю по-русски. Имена API, символов и команд сохраняй как в коде.

## Код и совместимость

- Rust 2021; следуй существующему стилю: `tokio`, `tracing`, `anyhow`/`thiserror`.
- Для новых публичных API пиши документацию о контракте и ошибках.
- Целевая среда Mini: ARM32/ELF32, A113X, glibc 2.23, около 236 MiB RAM.
  64-битный SoC не означает 64-битный userspace.
- Проверки на macOS не подтверждают Linux/ALSA и доступность `aplay` на Mini.
- Диагностическим копиям задавай отдельный `CARGO_TARGET_DIR`: общий cache
  может подставить binary другого snapshot. Не считать такой прогон baseline.
- Выбор musl target не доказывает статическую линковку всех native-зависимостей.
  Для ARM-артефакта проверяй ELF, interpreter, `NEEDED` и совместимость ALSA.
- Предпочитай ограниченные очереди, явные тайм-ауты и корректное завершение аудио,
  сетевых соединений и фоновых задач. Не логируй аудио или текст диалога по умолчанию.

## Выполнение задачи

1. **Фокус на одной задаче (Single-Task Rule):** браться строго за одну конкретную изолированную задачу за раз.
   Никогда не смешивать несколько требований в одном цикле. Завершить, покрыть тестами, проверить на стенде,
   закоммитить — только затем переходить к следующей задаче.
2. Прочитай `git status`, затронутые модули и инструкции; сохрани чужие изменения.
   При параллельной работе согласуй владельцев файлов; staging/коммиты
   выполняет только координатор. Не восстанавливай весь `src/` через checkout.
3. Назови ожидаемое поведение, риск и проверки. Для сложной задачи веди план.
4. Внеси ограниченное изменение и релевантные тесты поведения строго по плану.
5. Запусти проверки по [матрице](CONTRIBUTING.md#проверки).
   Для Rust-кода: `./scripts/check.sh`; предупреждения Clippy считаются ошибками.
6. Проведи ревью diff: ошибки, регрессии, совместимость, секреты, покрытие.
7. **Атомарные коммиты:** Коммитить только относящиеся к задаче файлы явным списком
   при каждом изменении кода с понятным Conventional Commits сообщением (`feat: ...`, `fix: ...`, `test: ...`).
8. **Авторизация только по подписке:** Использовать исключительно **OAuth-авторизацию по подписке
   (User Identity / Browser Login)**, подтверждающую аккаунт пользователя. Никаких платных API-ключей разработчика.
9. **Имя устройства:** В коде, mDNS, логах и конфигурациях использовать исключительно **`GPT Mini`**.
10. **Автономия пользователя (User Independence):** Пользователь не должен зависеть от агента
    для бытовой настройки. Смена голоса, модели, слова вызова, паттернов светодиода, Wi-Fi и перезагрузка
    должны управляться через локальный Web UI / Telegram App через файл `config.toml`, а не пересборкой кода.

## Секреты и устройство

- Секреты храни локально в `.env`/credential store; шаблоны содержат только заглушки.
  `.env`, `config.toml`, ключи и токены не должны попадать в Git, логи или ответы.
  Не исполняй dotenv через `source`/`eval`; не записывай в логи transcript,
  tool arguments, полный список домашнего оборудования или сырой ответ модели.
- Перед HA-действием исполнитель проверяет локальный allowlist сущностей,
  сервисов и параметров. System prompt/список устройств не ограничивает права.
  Без явной политики HA-действия должны быть отключены.
- Не запускай основной бинарь для обычной локальной проверки: он может включить
  микрофон, отправлять аудио в облако и вызывать сервисы Home Assistant.
- Не отключай и не удаляй `maind`, не меняй автозагрузку, OTA, boot или разделы
  в рамках обычного code-review/сборки. Для таких работ нужен отдельный план
  миграции с резервной копией и проверенным восстановлением в рамках задачи пользователя.
- Аппаратный тест выполняй только в согласованном объёме; фиксируй питание,
  версию/хеш бинаря, параметры аудио, наблюдения и восстановленное состояние.
  Hash указывай значением, а не словом «проверен». Не подставляй `hw:*` вместо
  проверенного `default` без отдельного исследования native формата устройства.
  Учитывай изменения сети/доступа в baseline и откате; frontend HA200 не
  подтверждает API-токен. Отказ SSH требует диагностики, а не обещания reboot.
